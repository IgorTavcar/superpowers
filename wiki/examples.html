The actual artifacts an agent runs

No metaphors on this page. These are the real templates, prompt fragments, and command blocks lifted from the skill files themselves — the exact text a Superpowers-equipped agent pastes, runs, and verifies. The methodology lives in this granularity: a task is five checkbox steps, a review is two ordered gates, a "done" is a fresh command output. Read it as a field manual.

Anatomy of a bite-sized TDD task

Every task in a Superpowers plan is the same shape. A Files block names exactly what to create, modify (with line ranges), and test — then five checkbox steps walk the agent through one full red-green cycle. Each step is one action of two to five minutes; nothing is left to interpretation.

★

One action per step. From writing-plans/SKILL.md: "Write the failing test" — step. "Implement the minimal code to make the test pass" — step. "Commit" — step. The plan literally bakes the TDD cycle into the checklist so the executing agent cannot skip a beat.

skills/writing-plans/SKILL.md — Task Structure
### Task N: [Component Name]

**Files:**
- Create: `exact/path/to/file.py`
- Modify: `exact/path/to/existing.py:123-145`
- Test: `tests/exact/path/to/test.py`

- [ ] **Step 1: Write the failing test**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **Step 2: Run test to verify it fails**

Run: `pytest tests/path/test.py::test_name -v`
Expected: FAIL with "function not defined"

- [ ] **Step 3: Write minimal implementation**

```python
def function(input):
    return expected
```

- [ ] **Step 4: Run test to verify it passes**

Run: `pytest tests/path/test.py::test_name -v`
Expected: PASS

- [ ] **Step 5: Commit**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```

The two Run lines carry an expected outcome — FAIL with "function not defined", then PASS — so the agent has a concrete prediction to check against, not a vague hope. And because each task ends in its own commit, the git history becomes a chain of green checkpoints you can review, bisect, or revert one at a time.

!

No placeholders. The same skill bans TBD, TODO, "add appropriate error handling", "Write tests for the above" without code, and even "Similar to Task N" — "repeat the code — the engineer may be reading tasks out of order."

The RED → GREEN → REFACTOR cycle

Those five steps are one pass through the cycle that governs all implementation. The mandatory verify phases — watch it fail, watch it pass — are what separate this from "write a test eventually."

01
RED
one minimal failing test
→
02
Verify RED
fails for the right reason
→
03
GREEN
simplest code, YAGNI
→
04
Verify GREEN
passes, suite green
→
05
REFACTOR
clean up, stay green
If you didn't watch the test fail, you don't know if it tests the right thing.
!

The Iron Law. test-driven-development/SKILL.md states it without hedging: "NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST." Wrote code before the test? Delete it — "Delete means delete," no keeping it as reference.

"If you didn't watch the test fail, you don't know if it tests the right thing."test-driven-development/SKILL.md

The two MANDATORY verify steps catch the two ways TDD silently breaks: a test that passes even before the code exists (it tests nothing), and a test that fails with an error rather than an assertion (it tests the wrong thing). REFACTOR runs only once the bar is green, and it adds no new behavior — clean-up is not an excuse to smuggle in features.

The mandatory plan header

Every plan document opens with a fixed header. It is not decoration — it is the wiring that tells the next agent which sub-skill to invoke, so an idle plan file on disk still knows how it is meant to be executed.

skills/writing-plans/SKILL.md — Plan Document Header
> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task.
> Steps use checkbox (`- [ ]`) syntax for tracking.

This is the hinge of the whole loop. brainstorming's only terminal transition is writing-plans; writing-plans stamps this header; the header names the two executors — subagent-driven-development (recommended) or executing-plans (inline). Pick one and you are routed into review, verification, and finishing without ever consulting a separate map.

✓

References by name, not by link. Skills point at each other with the superpowers:skill-name convention rather than @-file links — because @ force-loads the file and burns context before it's needed. The header declares the dependency; the agent loads it only when it gets there.

Two-stage review in practice

Under subagent-driven development, a fresh implementer subagent does each task, then hands off to two reviewers in a fixed order: spec-compliance first (built exactly what was asked — nothing more, nothing less), then code-quality (built well). Each reviewer loops fixes back to the same implementer until it returns clean.

01
Implementer
implement · test · commit
→
02
Spec Reviewer
FIRST · ✅ / ❌
→
03
Quality Reviewer
SECOND · only if ✅
→
04
Task Done
both clean

The implementer returns one of four statuses, so the controller always knows whether to advance, probe, or unblock:

skills/subagent-driven-development/implementer-prompt.md — Report Format
- **Status:** DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT

Then the spec reviewer opens with an instruction that sets the whole tone of the gate — it is told, in writing, not to take the implementer's word for anything:

"The implementer finished suspiciously quickly. Their report may be incomplete, inaccurate, or optimistic. You MUST verify everything independently."subagent-driven-development/spec-reviewer-prompt.md — "Do Not Trust the Report"

The reviewer reads the actual code line-by-line for missing requirements, extra unrequested work, and misunderstandings, returning ✅ or ❌ with a file:line reference. Order is non-negotiable — running the polish review before correctness is one of the skill's explicit Red Flags:

!

Red Flag (Never). "Start code quality review before spec compliance is ✅" — the wrong order. There is no point grading the craftsmanship of code that builds the wrong thing.

Requesting a review over a SHA range

A reviewer subagent is given a precise git range, not the session history — so it reviews the diff that matters and nothing else. The two lines below are how that range is captured.

skills/requesting-code-review/SKILL.md
BASE_SHA=$(git rev-parse HEAD~1)  # or origin/main
HEAD_SHA=$(git rev-parse HEAD)

Those SHAs fill placeholders in code-reviewer.md, the shared reviewer template (the same one the two-stage quality reviewer reuses). The reviewer checks plan alignment, code quality, architecture, testing, and production readiness — then sorts findings into Critical, Important, and Minor. The calibration note keeps that triage honest:

"Categorize issues by actual severity. Not everything is Critical. Acknowledge what was done well before listing issues — accurate praise helps the implementer trust the rest of the feedback."requesting-code-review/code-reviewer.md — Calibration
✓

Act by severity. The requester fixes Critical findings immediately, Important ones before proceeding, and notes Minor ones. The mirror skill — receiving-code-review — governs the other side: verify before implementing, no performative "You're absolutely right!", push back with technical reasoning when the reviewer is wrong.

Finishing the branch

When tests pass, finishing-a-development-branch presents exactly four options — never a default, never a silent merge. The agent verifies, detects the environment, then asks.

skills/finishing-a-development-branch/SKILL.md — Step 4
Implementation complete. What would you like to do?

1. Merge back to <base-branch> locally
2. Push and create a Pull Request
3. Keep the branch as-is (I'll handle it later)
4. Discard this work

Choose option 2 and the agent pushes the branch and opens a PR with a structured body — Summary plus Test Plan — built from a heredoc so the formatting is identical every time:

skills/finishing-a-development-branch/SKILL.md — Option 2
# Push branch
git push -u origin <feature-branch>

# Create PR
gh pr create --title "<title>" --body "$(cat <<'EOF'
## Summary
<2-3 bullets of what changed>

## Test Plan
- [ ] <verification steps>
EOF
)"
★

Provenance-based cleanup. The PR path deliberately leaves the worktree alive so you can iterate on review feedback. Cleanup happens only for merge and discard, and only for worktrees the framework owns (under .worktrees/, worktrees/, or ~/.config/superpowers/worktrees/) — and it always merges first, then removes the worktree, then deletes the branch.

Parallel agent fan-out

When several failures are genuinely independent — different files, different subsystems, no shared state — dispatching-parallel-agents sends one focused subagent per problem domain, all at once.

skills/dispatching-parallel-agents/SKILL.md
Task("Fix agent-tool-abort.test.ts failures")
Task("Fix batch-completion-behavior.test.ts failures")
Task("Fix tool-approval-race-conditions.test.ts failures")
// All three run concurrently

Each agent gets isolated, self-contained context: a specific scope, a clear goal, explicit constraints (for example, "Do NOT change production code"), and a required summary output. The controller then reads every summary, checks for cross-agent conflicts, runs the full suite to confirm the fixes compose, and spot-checks for systematic errors. In the skill's worked example, three parallel agents fix six failures across three files with zero conflicts.

Use it when

3+ test files fail with different root causes · multiple subsystems broken independently · no shared state between the failures.

Don't, when

The failures are related · full context is needed · it's exploratory debugging · the failures touch shared state. Then fall back to a single sequential investigation.

Root-cause tracing & the verification gate

For a single stubborn bug, systematic-debugging traces backward from the symptom to the original trigger — never patching where the error merely surfaces.

"NEVER fix just where the error appears. Trace back to find the original trigger."systematic-debugging/root-cause-tracing.md

When manual tracing dead-ends — say a stray .git keeps appearing and you can't tell which test creates it — a bisection tool isolates the polluting test by binary-searching the suite:

skills/systematic-debugging/root-cause-tracing.md — bisection
./find-polluter.sh '.git' 'src/**/*.test.ts'

Once you have a candidate fix, you do not get to call it fixed. The verification-before-completion gate demands a full red-green confirmation for any regression test — prove the test catches the bug by reverting the fix and watching it fail:

skills/verification-before-completion/SKILL.md — Regression tests
Write → Run (pass) → Revert fix → Run (MUST FAIL) → Restore → Run (pass)
!

The honesty gate. "NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE — If you haven't run the verification command in this message, you cannot claim it passes." A "should pass" is not evidence; a "probably" is not evidence; the agent's own success report is not evidence — only fresh output is.

That gate is what makes the rest of the page trustworthy. Every template, every review, every menu ends the same way: not with a confident sentence, but with a command that was actually run and an output that was actually read. See where it all gets used →
