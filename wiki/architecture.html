Architecture & cross-harness portability

Superpowers is a zero-dependency skill library plus bootstrap that installs across six coding-agent harnesses — Claude Code, OpenAI Codex, Cursor, Gemini CLI, GitHub Copilot CLI, and OpenCode — from a single canonical repo. One folder of Markdown is the source of truth; everything else is a thin adapter that teaches a given harness to find those skills and inject them at the right moment. This page is the engineering tour: the manifests, the polyglot hook, the three-branch JSON emitter, and the tool-name maps that let the same skill run everywhere.

Two pillars of a real integration

The contributor guide (CLAUDE.md, symlinked as AGENTS.md) doesn't leave "integration" to taste. It codifies the architecture as policy: a harness is only really integrated when it does two things.

① Discover the skills

The harness must find the skills/ directory and expose its 14 skills through a native skill tool. For hook-native harnesses this is automatic from the installed plugin; OpenCode reaches the same outcome by appending the path in JavaScript.

② Inject the bootstrap

At session start the harness must load the using-superpowers bootstrap — the introduction that makes the agent reach for skills unprompted. Discovery without injection is inert.

Pillar two is the one teams get wrong, and the guide is blunt about why it matters:

"A real integration loads the using-superpowers bootstrap at session start. The bootstrap is what causes skills to auto-trigger at the right moments. Without it, the skills are dead weight — present on disk but never invoked."CLAUDE.md
✓

The acceptance test. Any new harness has to pass one concrete check: send "Let's make a react todo list" in a clean session and confirm the brainstorming skill auto-triggers before any code is written. If the agent jumps straight to scaffolding a project, the bootstrap isn't landing.

The guide also draws hard lines around what is not a real integration: copying skill files in by hand, npx-style runtime shims, or per-session opt-in are all explicitly rejected. Two further rules round out the policy — zero third-party runtime dependencies, and every skill change must keep working across all supported harnesses, with PRs targeting the dev branch.

Repository layout

The repo is deliberately flat: one canonical skill library at the center, ringed by per-harness adapter manifests and the supporting machinery (hooks, scripts, docs, tests, assets).

The skills/ directory holds the entire library as sibling folders — brainstorming, writing-plans, executing-plans, test-driven-development, systematic-debugging, using-git-worktrees, subagent-driven-development, dispatching-parallel-agents, requesting-code-review, receiving-code-review, verification-before-completion, finishing-a-development-branch, writing-skills, and the eager-loaded using-superpowers. Each is a SKILL.md with YAML frontmatter plus optional references/, scripts/ (the brainstorming skill even ships a zero-dependency server.cjs visual companion), and *-prompt.md subagent templates.

★

Adapters are thin on purpose. Five of the six harnesses are just a manifest file at the repo root. Only OpenCode needs real code — and even that is one JavaScript file. The library never forks per harness; the adapters bend each harness toward the library.

The SessionStart bootstrap

The heart of portability is a single bash script, hooks/session-start. It reads the bootstrap skill, escapes it, wraps it in an unmissable envelope, and then emits one of three different JSON shapes depending on which harness is calling it.

First it reads skills/using-superpowers/SKILL.md, JSON-escapes the text (single C-level passes for backslash, quote, newline, carriage return, and tab), and wraps the result in an <EXTREMELY_IMPORTANT> envelope:

hooks/session-start — the envelope
session_context="<EXTREMELY_IMPORTANT>
You have superpowers.

**Below is the full content of your 'superpowers:using-superpowers' skill - your introduction to using skills. For all other skills, use the 'Skill' tool:**

${using_superpowers_escaped}

${warning_escaped}
</EXTREMELY_IMPORTANT>"

Then comes the portability trick. Different harnesses read session context from different JSON keys, so the script inspects environment variables and prints exactly the shape the current platform expects — using printf rather than a heredoc, because a heredoc triggers a hang on bash 5.3+ (issue #571):

hooks/session-start — the three-way branch
if [ -n "${CURSOR_PLUGIN_ROOT:-}" ]; then
    ...  printf '{\n  "additional_context": "%s"\n}\n' ...
elif [ -n "${CLAUDE_PLUGIN_ROOT:-}" ] && [ -z "${COPILOT_CLI:-}" ]; then
    ...  "hookSpecificOutput" ...
else
    ...  "additionalContext"  # Copilot sets COPILOT_CLI=1, or unknown (SDK standard)
Detected byHarnessJSON shape emitted
CURSOR_PLUGIN_ROOT setCursor{ "additional_context": … }
CLAUDE_PLUGIN_ROOT set, COPILOT_CLI unsetClaude Code{ "hookSpecificOutput": { "hookEventName": "SessionStart", "additionalContext": … } }
fallback (COPILOT_CLI=1, or unknown)Copilot / SDK{ "additionalContext": … } (top level)

The hook manifests select the event window. hooks/hooks.json fires on startup|clear|compact; hooks/hooks-cursor.json uses a lowercase sessionStart on a version-1 schema. Both invoke the same command, quoted so paths with spaces survive:

"command": "\"${CLAUDE_PLUGIN_ROOT}/hooks/run-hook.cmd\" session-start"

The script also detects a legacy ~/.config/superpowers/skills install and folds a one-time migration warning into the same envelope.

run-hook.cmd: a CMD/bash polyglot

Notice the command above points at run-hook.cmd, not the bash script directly. That one file is a genuine polyglot — valid input for both cmd.exe and bash — so the same hook entry works on Windows and Unix without branching in the manifest.

The first line, : << 'CMDBLOCK', makes bash swallow the entire Windows batch block as a no-op heredoc, while cmd.exe runs that block and ignores everything after it. The header even documents itself:

hooks/run-hook.cmd
: << 'CMDBLOCK'
@echo off
REM Cross-platform polyglot wrapper for hook scripts.
REM On Windows: cmd.exe runs the batch portion, which finds and calls bash.
REM On Unix: the shell interprets this as a script (: is a no-op in bash).
...
REM Try Git for Windows bash in standard locations
if exist "C:\Program Files\Git\bin\bash.exe" ( ... )
if exist "C:\Program Files (x86)\Git\bin\bash.exe" ( ... )
REM Try bash on PATH (e.g. user-installed Git Bash, MSYS2, Cygwin)
where bash >nul 2>nul
...
REM No bash found - exit silently rather than error
exit /b 0
CMDBLOCK

# Unix: run the named script directly
exec bash "${SCRIPT_DIR}/${SCRIPT_NAME}" "$@"

On Windows the batch block probes C:\Program Files\Git\bin\bash.exe, then the (x86) path, then where bash — and if none of those resolve, it exits 0 silently. The plugin still installs and works; it just won't get the session-start context injection. On Unix the colon no-op lets execution fall through to the exec bash line.

★

Two small details make it robust. Hook filenames are extensionless (session-start, not session-start.sh) because Claude Code's Windows auto-detection prepends bash to any command containing .sh — the bare name avoids a double-wrap. And .gitattributes forces LF line endings on hooks/session-start and *.cmd, so the polyglot stays parseable by both interpreters even after a Windows checkout.

OpenCode: a JS plugin, not a hook

OpenCode is the one harness that can't use the shell-hook path, so it gets the only real adapter code in the tree — a JavaScript plugin wired through package.json.

"main": ".opencode/plugins/superpowers.js"

The plugin exports two hooks. The config hook pushes the absolute skills/ path into config.skills.paths, so skills are discovered without symlinks — this works because OpenCode's Config.get() is a cached singleton. The second hook, experimental.chat.messages.transform, handles injection by unshifting the bootstrap onto the first user message:

.opencode/plugins/superpowers.js
const firstUser = output.messages.find(m => m.info.role === 'user');
...
// double-injection guard
if (firstUser.parts.some(p => p.type === 'text' && p.text.includes('EXTREMELY_IMPORTANT'))) return;
const ref = firstUser.parts[0];
firstUser.parts.unshift({ ...ref, type: 'text', text: bootstrap });

The design choices here are all hard-won. It injects as a user-message, not a system-message, deliberately: per issue #750 a system injection caused per-turn token bloat, and per #894 multiple system messages break Qwen. The bootstrap is built once and module-cached (_bootstrapCache, per #1202) because the transform hook fires on every agent step. A guard skips re-injection when the first user message already contains EXTREMELY_IMPORTANT. The JS even embeds its own OpenCode tool map inline, and install is via the opencode.json plugin array with a git+https spec.

One skill, every harness

The same skill Markdown runs on six harnesses because it is authored in exactly one vocabulary — Claude Code's tool names (Read, Write, Edit, Bash, Grep, Glob, Task, TodoWrite, Skill) — and each non-Claude harness gets a small mapping table the agent consults at execution time.

The bootstrap skill states the rule plainly and points each platform at its table:

"Skills use Claude Code tool names. Non-CC platforms: see references/copilot-tools.md (Copilot CLI), references/codex-tools.md (Codex) for tool equivalents. Gemini CLI users get the tool mapping loaded automatically via GEMINI.md."using-superpowers/SKILL.md

Gemini is the elegant case: no hook at all. gemini-extension.json declares contextFileName: GEMINI.md, and GEMINI.md is just two @-imports that pull the bootstrap and the tool map straight into context:

@./skills/using-superpowers/SKILL.md
@./skills/using-superpowers/references/gemini-tools.md

Gemini CLIGEMINI.md @-imports (no hook); activate_skillEdit → replace, Read → read_file, Bash → run_shell_command, Task → @generalist

The agent substitutes each Claude tool reference for its local equivalent on the fly. For skills that dispatch subagents, the harness mapping is supplemented by *-prompt.md templates the agent fills in and hands to that harness's native subagent system — so a parallel-agent skill works whether the underlying primitive is Codex's spawn_agent or Gemini's @generalist.

Version lockstep & Codex delivery

Six manifests that must agree on a version number is a recipe for drift. Superpowers solves it with a declarative manifest and a single bump script — and uses a separate sync script to deliver skills into the OpenAI Codex marketplace.

.version-bump.json names the six fields that must stay identical, and scripts/bump-version.sh bumps them all at once with drift detection and an --audit repo grep:

.version-bump.json
"files": [
  { "path": "package.json",                    "field": "version" },
  { "path": ".claude-plugin/plugin.json",      "field": "version" },
  { "path": ".cursor-plugin/plugin.json",      "field": "version" },
  { "path": ".codex-plugin/plugin.json",       "field": "version" },
  { "path": ".claude-plugin/marketplace.json", "field": "plugins.0.version" },
  { "path": "gemini-extension.json",           "field": "version" }
]

Codex is a special case because .codex-plugin/ only commits a plugin.json (carrying a rich interface block — displayName, capabilities, defaultPrompt, brandColor, composer icon/logo from assets/). The skills themselves are delivered by scripts/sync-to-codex-plugin.sh, which mirrors the repo into the OpenAI marketplace fork prime-radiant-inc/openai-codex-plugins at plugins/superpowers:

  1. Clone & rsync

    Copies tracked upstream content into plugins/superpowers, excluding all non-Codex harness infra — .claude-plugin/, .cursor-plugin/, .opencode/, hooks/, docs/, tests/, scripts/, GEMINI.md, gemini-extension.json, package.json.

  2. Preserve OpenAI metadata

    Keeps any OpenAI-owned skills/*/agents/openai.yaml files already in the destination.

  3. Branch, push, PR

    Commits the sync to a branch and opens a deterministic pull request — the channel through which Codex receives skills despite committing only a manifest in-repo.

The Cursor manifest is the other outlier: it uniquely declares agents/ and commands/ directories (which do not exist at the repo root in this checkout) alongside its hook file.

"skills": "./skills/",
  "agents": "./agents/",
  "commands": "./commands/",
  "hooks": "./hooks/hooks-cursor.json"

The mechanisms, recapped

Four moving parts carry the entire portability story. Strip them down and the architecture fits on a postcard.

Bootstrap injection

A SessionStart event runs the polyglot, which execs hooks/session-start. That script wraps the bootstrap in an <EXTREMELY_IMPORTANT> envelope and prints the JSON shape the current platform consumes — chosen by env-var detection. Gemini does it via @-imports; OpenCode via a cached first-user-message transform.

Skill discovery

Skills live as skills/<name>/SKILL.md with "Use when…" frontmatter triggers. Hook-native harnesses auto-discover them; OpenCode appends the path in JS. The bootstrap loads eagerly; every other skill loads lazily on demand.

Tool-name mapping

Skill bodies are written only in Claude Code tool names. Each non-Claude harness reads a references/<harness>-tools.md table (or inline map) and substitutes local equivalents at run time — no per-harness skill forks.

Lockstep & sync

.version-bump.json + bump-version.sh keep six manifests on one version; sync-to-codex-plugin.sh mirrors skills into the OpenAI Codex marketplace fork and opens a PR.

One library of Markdown. Six harnesses. The skills are dead weight until the bootstrap makes them auto-trigger — and that single idea is the whole architecture.
