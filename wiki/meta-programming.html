Agentic Meta-Programming

Stop reading Superpowers as documentation. Read it as source code. A skill is a reusable, version-controlled procedure — a prompt-program — that teaches a coding agent an expert workflow. The skills compose at runtime into a full development methodology, and one skill, writing-skills, is a program whose output is other programs. This is the conceptual heart of the whole repo: meta-programming, but the interpreter is a large language model.

Skills are code, not prose

The repo states its governing thesis in three words inside its own CLAUDE.md, and once you accept it the entire design falls into place.

"Skills are not prose — they are code that shapes agent behavior."Superpowers CLAUDE.md

Anthropic supplies the substrate. In its October 2025 engineering post it defines a skill as a directory containing a SKILL.md file whose YAML frontmatter carries two required fields — name and description — plus optional bundled scripts and resources. Crucially, skills can ship executable code that Claude runs via bash, and "the script's code never loads into the context window. Only the script's output… consumes tokens." A skill is therefore not a prompt you paste; it is a filesystem-backed resource that the agent discovers, pages in, and executes.

Superpowers takes that primitive and treats the whole library as a programming system. Each procedure is plain Markdown, but it is authored, version-controlled, and adversarially tested the way a codebase is. The agent is the CPU; the skills are the instructions; git is the package manager. The framework's own README puts the ambition in one sentence:

❝

The thesis. "Superpowers is a complete software development methodology for your coding agents, built on top of a set of composable skills and some initial instructions that make sure your agent uses them." — Superpowers README

It doesn't make the model smarter. It hands the model a library of procedures it can call — and the discipline to actually call them.

Three layers of the program

What turns a folder of Markdown into a program library is the separation of concerns. Three distinct layers do three distinct jobs: find the right procedure, force the agent to run it, and chain procedures into a workflow.

①

Discovery / index

Only frontmatter — name + description — is pre-loaded into the system prompt at startup (~100 tokens per skill). The description is a pure trigger predicate answering one question: "should I read this skill now?" The bodies stay on disk until needed.

②

Control

The using-superpowers bootstrap, loaded at session start, routes every user message through a mandatory gate before the agent acts. This is what makes skills auto-trigger instead of sitting inert on disk.

③

Composition

Skills tail-call each other with explicit terminal states. brainstorming hands off to writing-plans, which hands off to worktrees and execution — a call graph of prompt-programs with return semantics.

Map those layers onto Anthropic's own three levels of progressive disclosure and they line up exactly: metadata pre-loaded ("just enough information for Claude to know when each skill should be used without loading all of it into context"), the SKILL.md body loaded only when judged relevant, and bundled files navigated only as needed — "effectively unbounded" context at near-zero idle cost. Superpowers adds the missing control layer that the bare standard leaves to the host: a bootstrap that actually pulls the trigger.

The 1% rule

A program library is worthless if the runtime never calls into it. The using-superpowers bootstrap solves the hardest problem in the whole design — getting the agent to stop and look — with a single, deliberately extreme threshold.

"If you think there is even a 1% chance a skill might apply to what you are doing, you ABSOLUTELY MUST invoke the skill. … You cannot rationalize your way out of this."Superpowers using-superpowers/SKILL.md

The bootstrap is loaded at session start, so the gate runs without any per-session opt-in. Every incoming message is routed through one question — "Might any skill apply?" — answered yes on even a 1% chance. When the answer is yes, the agent must do three things in order before it does anything else:

  1. Invoke

    Call the Skill tool and actually read the procedure. No working from memory — a remembered skill is not a loaded skill.

  2. Announce

    Say it out loud: Using [skill] to [purpose]. A public commitment is harder to abandon mid-task than a private intention.

  3. Convert to TodoWrite

    Turn each checklist item into a TodoWrite todo, then follow the skill exactly. The todo list becomes a commitment device the agent can't quietly skip.

A Red Flags table pre-empts the specific evasions the model reaches for — "This is just a simple question" is met with "Questions are tasks. Check for skills." Without this control layer, the rest of the library is, in the repo's own words, "dead weight — present on disk but never invoked." The acceptance test in CLAUDE.md is blunt: typing "Let's make a react todo list" must auto-trigger the brainstorming skill before a single line of code is written.

!

Why so aggressive? The bootstrap is fighting the model's default helpfulness. Left alone, an agent jumps straight to code. The 1% rule deliberately over-triggers so that the cost of a false skip — silently abandoning the methodology — never gets paid.

writing-skills: a program that writes programs

Here is the self-referential core. The tool that produces the agent's procedures is itself a disciplined engineering procedure — and the discipline it uses is Test-Driven Development.

"Writing skills IS Test-Driven Development applied to process documentation."Superpowers writing-skills/SKILL.md

Every TDD concept maps cleanly onto authoring. The test is a pressure scenario run against a fresh subagent. The production code is the SKILL.md. You must watch the agent fail without the skill before you write it — because "if you didn't watch an agent fail without the skill, you don't know if the skill teaches the right thing." Then you write the minimal skill that fixes exactly those observed failures, re-run, and harden.

The whole thing is enforced by an Iron Law, applied to brand-new skills and to edits alike:

★

Iron Law. NO SKILL WITHOUT A FAILING TEST FIRST. "Write skill before testing? Delete it. Start over." The meta-skill holds itself to the same standard it teaches everything else.

Jesse Vincent describes the bootstrap of the bootstrap plainly: "One of the first skills I taught Superpowers was How to create skills." A framework that can author its own procedures — tested like code, version-controlled like code — is self-extending. That is the precise sense in which Superpowers is agentic meta-programming.

Description = WHEN, not WHAT (Claude Search Optimization)

The index layer hangs entirely on one field — the description — and one of the project's sharpest empirical findings is about how to write it. The rule is counterintuitive: describe only when to use the skill, never what it does.

"CRITICAL: Description = When to Use, NOT What the Skill Does … Testing revealed that when a description summarizes the skill's workflow, Claude may follow the description instead of reading the full skill content."Superpowers writing-skills/SKILL.md

The failure mode is concrete and a little alarming. A description that summarized a workflow caused Claude to act on the summary and skip the real procedure. In the documented case, a description saying code review happens "between tasks" caused Claude to do one review — even though the skill's flowchart clearly showed two. The agent winged it from the metadata. The fix was to strip the description down to a pure trigger predicate, which sent Claude back to the flowchart, and it did both reviews.

The trap — workflow summary

do not

"Reviews code for quality and spec compliance between implementation tasks, running two passes…"

Claude follows the sentence and skips the body. It did one review instead of two.

The fix — trigger predicate

do

"Use when you have just finished a task and are about to start the next one…"

A pure "should I read this now?" question. Claude reads the flowchart and follows it.

The conventions follow from this: start with "Use when…", write in the third person (it is injected straight into the system prompt), cap it at 1024 characters, and name the skill verb-first — creating-skills, not skill-creation. Call it Claude Search Optimization: the description isn't advertising copy, it's a retrieval key. Note one subtlety worth flagging — Anthropic's own platform spec asks the description to state "both what the skill does and when to use it," whereas Superpowers found that, under its strict-compliance skills, the "what" half actively backfires.

Hardening against the interpreter

Here is what makes these prompt-programs unlike ordinary code: the interpreter is clever, and under pressure it will argue with its own instructions. So the discipline skills are deliberately bulletproofed against the agent's own ingenuity.

The repo is candid about why: "Agents are smart and will find loopholes when under pressure." The toolkit for closing those loopholes is layered, and every layer is built from real failures captured during testing:

Foundational cut

A single early principle kills the largest class of evasions: "Violating the letter of the rules is violating the spirit of the rules." No more "technically I followed it."

Explicit loophole negation

Spell out the escape and close it: "Delete it. Start over. … Don't keep it as reference. … Delete means delete."

Rationalization Tables

A two-column Excuse | Reality table built verbatim from baseline test transcripts, so each real rationalization gets a pre-written rebuttal.

Red Flags & HARD-GATEs

Self-check thoughts that all resolve to "STOP and start over," plus hard gates like brainstorming's: "Do NOT invoke any implementation skill… until the user has approved it."

None of this is folk wisdom — it's grounded in persuasion research. The persuasion-principles.md reference cites Meincke et al. (2025), a study across roughly 28,000 AI conversations, where the right techniques "more than doubled compliance rates (33% → 72%, p < .001)." Those levers are deployed deliberately: authority (imperative "YOU MUST", "No exceptions"), commitment (announce usage, force an explicit A/B/C choice, track via TodoWrite), and social proof. Because this content is empirically tuned, CLAUDE.md forbids editing it without eval evidence.

"Persuasion techniques more than doubled compliance rates (33% → 72%, p < .001)."Meincke et al. (2025), cited in persuasion-principles.md

Flowcharts as control flow

When a skill needs to express branching logic, it doesn't write prose — it draws a Graphviz dot digraph. The flowchart is the control-flow notation of the prompt-program, with a typed visual grammar.

The discipline is precise: flowcharts are for non-obvious decision points, process loops where you might stop too early, and "when to use A vs B" choices — and for nothing else. Reference material uses tables, code uses Markdown, linear steps use numbered lists. The graphviz-conventions.dot file defines a strict typed grammar so every diagram in the corpus reads the same way:

ShapeMeans
diamonda question / decision
boxan action
plaintexta command to run
ellipsea state
red octagona warning / stop
doublecircleentry / exit point
dotted edge"triggers" another skill
skills/writing-skills/graphviz-conventions.dot
digraph decision {
  start   [shape=doublecircle, label="user message"];
  apply   [shape=diamond,      label="Might any skill apply?"];
  invoke  [shape=box,          label="Invoke the skill"];
  wing    [shape=octagon, color=red, label="STOP: do not wing it"];

  start  -> apply;
  apply  -> invoke [label="yes (even 1%)"];
  apply  -> wing   [label="no — are you sure?"];
}

The using-superpowers gate, the RED-GREEN-REFACTOR cycle, and the brainstorming spec-review loop are all expressed this way, and render-graphs.js turns them into SVG for the human partner to read. Two things are explicitly forbidden inside nodes: actual code, and semantically-empty labels like step1 or helper2. The diagram has to carry real meaning, not decoration.

Testing skills with subagents & progressive disclosure

If skills are programs, what is the test harness? Other agents. A fresh subagent is the unit-test fixture — a clean interpreter with no context contamination.

The pattern descends from Anthropic's "Claude A / Claude B" loop: Claude A authors and refines the skill; Claude B, a fresh instance with the skill loaded, executes real tasks; the gaps in Claude B's behavior go back to Claude A. Superpowers sharpens this into adversarial pressure-testing. Scenarios use real file paths, force a concrete choice — "What do you do?" not "What should you do?" — allow no easy out, and combine three or more pressures at once:

time sunk cost authority economic exhaustion social pragmatic

You run the subagent without the skill first to capture its rationalizations verbatim, then plug each one. When the agent makes a wrong choice you do meta-testing: ask it how the skill should have been written. The answers sort into three buckets — "the skill was clear, I ignored it" (needs a stronger foundational principle), "it should have said X" (add it verbatim), or "I didn't see section Y" (reorganize). A skill is bulletproof when the agent picks the right option under maximum pressure and cites the skill while doing it.

That subagent-as-fixture mirrors the runtime itself: subagent-driven-development dispatches a fresh subagent per task for exactly the same context-isolation reason. And it depends on the last piece of the puzzle — progressive disclosure used as a filesystem-backed virtual memory. References are kept one level deep from each SKILL.md, bodies stay under tight token budgets, and there is a hard rule against @-links:

"Why no @ links: @ syntax force-loads files immediately, consuming 200k+ context before you need them."Superpowers writing-skills/SKILL.md

The agent pages in exactly the procedure it needs, exactly when it needs it. Put it all together and you have the full picture: natural-language procedures, version-controlled and adversarially tested like code, that a smart-but-rationalizing interpreter executes reliably — even under pressure. That is what Superpowers means by treating skills as code.
