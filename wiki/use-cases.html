Use Cases: where the discipline pays off

Superpowers is not a magic wand for every keystroke — it's a methodology that earns its keep on work that used to fall apart. Below are the scenarios where practitioners and the repo's own skills converge: each framed as a situation, how the framework handles it, and the payoff. Every claim here is grounded in the skill files and real practitioner reports — not in marketing.

Shipping big multi-file features

The classic failure mode of stock agentic coding: a feature that touches a dozen files, where the agent loses the thread halfway through and leaves you to reconcile the inconsistencies by hand.

The situation

Richard Porter describes the old loop bluntly: "describe the feature, hope Claude understood... watch it write code for 10 minutes, then spend an hour fixing the inconsistencies."

How Superpowers handles it

The flow is brainstorm → write-plan → execute-plan with TDD. Plans are broken into 12–15 tasks of ~2–5 minutes each, with file paths and acceptance criteria baked in.

The payoff

Features spanning 15+ files execute consistently with fewer regressions — because, in Porter's words, "each subagent starts fresh with only the context it needs."

"Claude literally cannot skip the planning phase or write code before tests."Richard Joseph Porter
★

Why it works. Context is the scarce resource. A fresh implementer subagent per task means the model never has to hold fifteen files in its head at once — it gets exactly the slice it needs, does one bite-sized job, and hands back a verified commit.

Spec-first to kill rework

Most wasted agent-hours come from building the wrong thing confidently. The fix is to refuse to build anything until intent is unambiguous.

The brainstorming skill carries a HARD-GATE that forbids any implementation action before you approve a design — and it explicitly rejects the rationalization "this is too simple to need a design." It explores the codebase, asks clarifying questions one at a time, proposes 2–3 approaches with tradeoffs, then writes an editable Markdown design doc you can comment on in your own editor before a single line of code exists.

"Do NOT invoke any implementation skill, write any code, scaffold any project, or take any implementation action until you have presented a design and the user has approved it."brainstorming/SKILL.md — the HARD-GATE
An hour spent on a spec you actually read beats a day spent unwinding code you never wanted. The doc is the artifact you correct, cheaply, before anything is built.

Evan Schwartz's "A Rave Review" praises exactly this: being able to weigh in on a concise ~dozen-bullet outline rather than rewriting a multi-page default Plan-mode doc. His verdict is unambiguous.

"Using Claude Code with Superpowers is so much more productive and the features it builds are so much more correct than with stock Claude Code."Evan Schwartz, "A Rave Review of Superpowers"

Autonomous task execution

Once a plan exists, the goal is to let the agent run without babysitting — and without drifting off-plan. This is where the framework's structure becomes leverage.

  1. Controller reads the plan once

    It extracts every task's full text plus context and builds a TodoWrite list — the subagents never have to read the plan file themselves.

  2. Fresh implementer subagent per task

    The controller pastes the full task text into a focused implementer that implements, tests, commits, and self-reviews — then reports one of four statuses: DONE, DONE_WITH_CONCERNS, NEEDS_CONTEXT, or BLOCKED.

  3. Two-stage review keeps it honest

    A spec-compliance reviewer runs first, a code-quality reviewer second — each looping until clean before the task is marked complete.

✓

The payoff. Because each task is small, isolated, and gated, the loop can run a long time without supervision while staying on the rails. The plan is the leash — and the agent literally cannot wander off it.

The framework's own principle states the bet plainly:

"Fresh subagent per task + two-stage review (spec then quality) = high quality, fast iteration."subagent-driven-development/SKILL.md

Test-enforced bug fixes

Agents love to say "I'll write the test after." Under Superpowers, that sentence is not a deferral — it's a deletion order.

The test-driven-development skill enforces an Iron Law and a hard consequence: write production code before its failing test, and the rule is "Delete it — Delete means delete." The mechanism is the point. As Marc Nuri's analysis puts it, the model can already lecture you on TDD; what it lacks is a mechanism that holds it to those concepts when shortcuts are easier.

"NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST."test-driven-development/SKILL.md — The Iron Law

The discipline IS the feature

The cycle is Red → Verify-Red → Green → Verify-Green → Refactor, with a mandatory watch-it-fail step. "If you didn't watch the test fail, you don't know if it tests the right thing."

Regressions get the full cycle

A fix isn't trusted until the test is proven to catch the bug: Write → Run (pass) → Revert fix → Run (MUST FAIL) → Restore → Run (pass).

"[The TDD skill] treats 'I'll write the test after' as grounds to delete the implementation and start over."Marc Nuri, technical analysis of Superpowers

Hunting a gnarly root cause

The bug that makes you want to throw your laptop: a symptom buried deep in the stack, far from its true cause. The systematic-debugging skill forbids the reflexive patch.

"NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST."systematic-debugging/SKILL.md — The Iron Law

The skill's root-cause-tracing.md companion carries a worked example that captures the whole philosophy. A stray .git appeared in packages/core. Rather than deleting the directory and moving on, the trace went backward through five levels to the true trigger:

01
.git in packages/core
the symptom
→
02
git init in empty cwd
WorktreeManager
→
03
Session.create
passes the bad cwd
→
04
test reads tempDir
before beforeEach
→
05
setupCoreTest
returns {tempDir:''}

The fix was at the source — a getter that throws when accessed too early — plus four layers of defense-in-depth so the bug becomes impossible to reintroduce. When manual tracing dead-ends, the skill reaches for a bisection tool to find which test pollutes shared state:

find-polluter.sh
./find-polluter.sh '.git' 'src/**/*.test.ts'
✓

The payoff. Real-world impact from that one investigation: 1847 tests passed, zero pollution. Trace to the trigger, fix at the source, defend every layer — and the class of bug is gone, not just this instance.

★

The escalation rule. If three fixes fail, the skill orders you to stop and question the architecture: "This is NOT a failed hypothesis — this is a wrong architecture." It refuses to let you stack patches on a broken foundation.

Parallel fan-out for independent failures

When a test suite breaks in several unrelated places at once, sequential debugging is wasted wall-clock time. The dispatching-parallel-agents skill turns that into a fan-out.

The trigger is specific: 3+ test files failing with different root causes, multiple subsystems broken independently, and no shared state. The skill groups failures into independent problem domains and dispatches one focused, self-contained agent per domain — concurrently. Its real example fixes 6 failures across 3 files with 3 parallel agents, zero conflicts.

Task("Fix agent-tool-abort.test.ts failures")
Task("Fix batch-completion-behavior.test.ts failures")
Task("Fix tool-approval-race-conditions.test.ts failures")
// All three run concurrently

The controller then reads each summary, checks for cross-agent conflicts, runs the full suite to confirm the fixes compose, and spot-checks for systematic errors.

!

When NOT to fan out. The skill is explicit: do not use parallel agents for related failures, when full context is needed, for exploratory debugging, or when failures share state. Those cases fall back to a single sequential investigation.

Disciplined code review & clean finishes

A feature isn't done when the code runs — it's done when it's been reviewed honestly and landed cleanly. Two skills govern the endgame.

Review by severity, no flattery

requesting-code-review dispatches a Senior Reviewer over a git SHA range with calibrated severity. receiving-code-review forbids performative agreement entirely.

Finish with exactly four options

finishing-a-development-branch re-verifies tests, then presents Merge / Push+PR / Keep / Discard — with provenance-based worktree cleanup so nothing is left dangling.

"Categorize issues by actual severity. Not everything is Critical. Acknowledge what was done well before listing issues — accurate praise helps the implementer trust the rest of the feedback."requesting-code-review/code-reviewer.md

And the reception side is deliberately unsentimental — "You're absolutely right!" is called out as an explicit CLAUDE.md violation. The instruction is blunt: if you catch yourself about to write "Thanks," delete it and state the fix instead. Feedback is evaluated, verified against this codebase, and pushed back on with technical reasoning when the reviewer is wrong.

The finish itself is a clean menu, not a guess:

finishing-a-development-branch — Step 4
Implementation complete. What would you like to do?

1. Merge back to <base-branch> locally
2. Push and create a Pull Request
3. Keep the branch as-is (I'll handle it later)
4. Discard this work

Across harnesses & teams

Because the skills are plain Markdown plus a tiny bootstrap, the same methodology travels — and it composes with the parallel-work tooling people actually use.

Marc Nuri describes the framework as "a directory of fourteen skills, each a single SKILL.md file" with a bootstrap hook under 2,000 tokens, portable across Claude Code, Cursor, and Copilot CLI. Practitioners take that portability further: Chandler combines Claude Code + Conductor + Superpowers to run parallel worktrees across multiple repos, feeding in Linear/GitHub issues and research, motivated by eliminating the "dead time" of watching a single agent.

"The planning part of Superpowers is definitely the reason it performs so much better."Chandler (chand1012), "The best way to do agentic development in 2026"
★

It plays well with others. Some teams stack it: gstack for architectural decision-making, GSD for long-session context stability, and Superpowers for disciplined execution. As one writeup summarizes — "gstack thinks, GSD stabilizes, Superpowers executes."

When NOT to reach for the full ceremony

An honest reference page says where the tool doesn't fit. The five-phase process is leverage on hard problems — and overhead on trivial ones.

For "fast iterative design work like changing a button color," the five-phase process slows you down. For small, contained fixes, the plan-generation overhead may cost more tokens than just executing — and reviewers note that skills "load fully into context on every invocation," which adds up.

Task shapeFull ceremony?Why
One-line button-color changeNoPlan + review overhead dwarfs the change; pure token cost
Small contained bug fixUsually notOften faster to just execute than to generate a plan
Feature spanning 15+ filesYesFresh-context subagents prevent the inconsistency tax
Gnarly cross-component bugYesRoot-cause tracing beats hours of symptom-patching

The numbers back up the nuance. One benchmark-style writeup found roughly a 14% token cut and a quality boost on complex tasks — but no benefit on simple ones. The lesson isn't "always" or "never"; it's "match the ceremony to the complexity."

!

The honest caveat. Skeptics on Hacker News warn that "without benchmarks or some kind of evaluation... this could make Claude worse." Superpowers is discipline, not a free lunch — its value scales with the difficulty of the work. For a deeper, both-sides look at the reception, see From the Web.
