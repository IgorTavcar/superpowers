The Brainstorming Engine

Before a single line of code, a Superpowers agent slows down and asks what you're really trying to build. brainstorming is a gated, one-question-at-a-time Socratic method that teases a spec out of the conversation — and, when seeing beats reading, it can spin up a live browser companion that streams mockups at you as you talk. Two parts: a disciplined interview, and a zero-dependency server that turns the chat into a clickable surface.

Socratic by design

SKILL.md defines brainstorming not as a vibe but as a method: a hard-gated checklist of nine ordered tasks, each created as a tracked task so the agent can't skip ahead. The whole point is to convert a fuzzy request into an approved design without ever writing code on a guess.

  1. Explore project context

    Read the lay of the land before asking anything — what exists, what conventions hold, where this fits.

  2. Offer the visual companion

    A single isolated message offering the live browser tool. Nothing else in that message.

  3. Ask one question at a time

    Multiple-choice preferred, one question per message. No question barrages.

  4. Propose 2–3 approaches

    Each with trade-offs and an explicit recommendation — not a menu, a point of view.

  5. Present the design in sections

    Scaled to complexity, getting approval after each section before moving on.

  6. Write & commit the spec

    To docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md, then commit it.

  7. Self-review the spec

    A fresh-eyes pass for placeholders, consistency, scope, and ambiguity.

  8. Get explicit user review

    Report the spec path, wait, and loop on requested changes.

  9. Invoke writing-plans

    The one and only terminal state — never frontend-design, never mcp-builder.

!

The HARD-GATE. This is the rule that makes brainstorming more than a suggestion:

"Do NOT invoke any implementation skill, write any code, scaffold any project, or take any implementation action until you have presented a design and the user has approved it. This applies to EVERY project regardless of perceived simplicity."skills/brainstorming/SKILL.md — HARD-GATE

There's a named anti-pattern for exactly the excuse you're tempted to make: "this is too simple to need a design." The skill rejects it outright. Every project gets a presented-and-approved design first, full stop.

The interview is the product. By the time code is written, the hard decisions are already made, visible, and signed off.

Scope first

There is no literal "how big is this?" questionnaire. Instead, before refining any detail, the agent makes a scope judgement — because the most expensive mistake is designing one giant thing when you actually asked for three.

Detect the multi-subsystem request

If a request "describes multiple independent subsystems," the agent is told to flag this immediately rather than plowing into details for a monolith that shouldn't exist.

Decompose into sub-projects

Oversized work is broken into independent pieces — their relationships and build order mapped — and each sub-project gets its own spec → plan → implementation cycle.

✦

YAGNI, ruthlessly. The guidance is blunt: "Remove unnecessary features from all designs." Paired with design-for-isolation — small, well-bounded units with one clear purpose — scope discipline keeps each resulting spec to a single plan's worth of work.

The spec, reviewed twice

Once a design is approved section by section, it gets written down — and then it gets read twice. Once by the agent with fresh eyes, once by you with a veto.

where the spec lands
docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md   (written, then committed)

The self-review is a deliberate fresh-eyes pass with four checks, fixed inline with no second re-review:

CheckWhat it hunts for
Placeholder scanStray TBD / TODO / vague hand-waving that never got resolved.
Internal consistencySections that contradict each other or drift from the agreed approach.
ScopeDoes this still fit a single plan, or did it quietly grow into a decomposition?
AmbiguityPick one interpretation and make it explicit — don't leave a fork for later.

Then the user-review gate: the agent reports the spec path, waits, and on any requested change edits the spec and re-runs the review loop. It only proceeds to writing-plans once you've approved. Nothing slips through on momentum.

A tool, not a mode

Now the fun half. The visual companion is, in the skill's own framing, "available as a tool — not a mode." Turning it on doesn't move the whole conversation into the browser. It's offered exactly once, and then used surgically.

★

The offer is isolated. The message that offers the companion must "contain ONLY the offer above and nothing else" — and it warns you the feature is new, token-intensive, and needs you to open a local URL. No bundling it with a real question.

Even after you accept, the companion doesn't fire on every turn. The agent decides per question with a single test:

"would the user understand this better by seeing it than reading it?"skills/brainstorming/SKILL.md

→ Browser

Visual artifacts. Mockups, wireframes, architecture diagrams, side-by-side comparisons — things that are genuinely clearer as pixels.

→ Terminal

Words. Requirements, conceptual A/B/C choices, trade-off lists, scope. A question about a UI topic isn't automatically a visual question.

That distinction matters: the test is about the answer's medium, not its subject. "Which color scheme?" might be visual; "should we support themes at all?" is a sentence in the terminal.

Zero dependencies

The runtime behind the companion is a single file — skills/brainstorming/scripts/server.cjs — a Node HTTP server that imports nothing but built-ins: http, crypto, fs, path. The 2026-03-11 redesign that produced it had a stark before-and-after.

714 → 0
vendored node_modules files, eliminated
4
built-in modules, nothing else
1003
close code for an unknown WS opcode

Gone are express, ws, and chokidar — replaced by hand-rolled equivalents. The most interesting bit is the RFC 6455 WebSocket implemented from scratch. The handshake is the classic SHA-1 dance against the magic GUID:

server.cjs — the WebSocket handshake
computeAcceptKey =
  base64( SHA-1( clientKey + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11" ) )

From there, encodeFrame/decodeFrame handle all three length encodings (under 126, 16-bit, 64-bit). Server frames go out unmasked; client frames must be masked and are XOR-unmasked on the way in. Only four opcodes are honored — TEXT, CLOSE, PING, PONG — and anything unrecognized closes the connection with status 1003. The protocol functions are dual-exported so a unit test can drive them, and the server only actually binds a port when require.main === module.

✦

Why bother? A brainstorming helper that drags 714 third-party files into every session is a liability — supply chain, install time, version drift. A 4-built-in server is something you can read top to bottom and trust. That ethos is the whole framework, distilled: see Architecture.

content/ vs state/

A companion session lives under <project>/.superpowers/brainstorm/<PID>-<epoch>/ (or under /tmp when no --project-dir is given). Inside, the directory is split in two — and the split is the load-bearing design decision.

content/

The agent-written HTML screens. fs.watch watches this directory, and GET / serves the newest file by mtime. This is what the browser actually displays.

state/

Pure IPC: server-info, events, and server-stopped (plus server.pid / server.log from the start script). This is how the agent and server talk.

★

Why the peer split. state/ is deliberately a sibling of content/, not a file inside it — because content/ is served over HTTP and state/ must never be. Keeping the click-event log and IPC files out of the served tree means a stray request can't ever leak the brainstorm's internal state to the browser.

This is also a spot where the shipped engine has quietly outrun its own spec: the 2026-03-11 design described a single flat SCREEN_DIR with hidden dotfiles (.events, .server-info). The code that actually shipped promoted those to a non-hidden state/ peer and added server-stopped. Before every write, the agent checks that state/server-info exists and state/server-stopped does not.

The watcher is debounced ~100ms and keyed off a knownFiles set rather than the event type — because macOS reports 'rename' for both brand-new files and overwrites. On a genuinely new screen it clears the stale state/events log; either way it broadcasts a reload:

server.cjs — fs.watch handler
if (!knownFiles.has(filename)) {
  knownFiles.add(filename);
  const eventsFile = path.join(STATE_DIR, 'events');
  if (fs.existsSync(eventsFile)) fs.unlinkSync(eventsFile);
  console.log(JSON.stringify({ type: 'screen-added', file: filePath }));
} else {
  console.log(JSON.stringify({ type: 'screen-updated', file: filePath }));
}

broadcast({ type: 'reload' });

When the browser re-fetches /, the server reads the newest screen and decides whether to pass it through or dress it up. A full document (it starts with <!doctype or <html>) is served as-is; a bare fragment gets dropped into frame-template.html's <!-- CONTENT --> slot — and either way, helper.js is injected before </body>:

server.cjs — GET /
const screenFile = getNewestScreen();
let html = screenFile
  ? (raw => isFullDocument(raw) ? raw : wrapInFrame(raw))(fs.readFileSync(screenFile, 'utf-8'))
  : WAITING_PAGE;

On the client, helper.js opens ws://host, reloads on a 'reload' message, and reconnects after 1s if the socket drops — buffering any events in an eventQueue until the connection is back. A single document-level click listener walks up to the nearest [data-choice] ancestor and fires the selection:

helper.js — click capture
const target = e.target.closest('[data-choice]');
if (!target) return;

sendEvent({
  type: 'click',
  text: target.textContent.trim(),
  choice: target.dataset.choice,
  id: target.id || null
});

Back on the server, handleMessage stamps activity, logs the event, and appends it to state/events — but only if it actually carries a choice, so idle hover noise never pollutes the log the agent reads:

server.cjs — handleMessage
touchActivity();
console.log(JSON.stringify({ source: 'user-event', ...event }));
if (event.choice) {
  const eventsFile = path.join(STATE_DIR, 'events');
  fs.appendFileSync(eventsFile, JSON.stringify(event) + '\n');
}
★

The companion in one sentence, from visual-companion.md: "The server watches a directory for HTML files and serves the newest one to the browser. You write HTML content to screen_dir, the user sees it in their browser and can click to select options. Selections are recorded to state_dir/events that you read on your next turn."

Lifecycle & the turn loop

A long-lived local server tied to an agent session needs to die gracefully — when the agent's gone, or when the conversation's gone quiet. A 60-second supervisor handles both.

server.cjs — lifecycle supervisor
function ownerAlive() {
  if (!ownerPid) return true;
  try { process.kill(ownerPid, 0); return true; } catch (e) { return e.code === 'EPERM'; }
}

// Check every 60s: exit if owner process died or idle for 30 minutes
const lifecycleCheck = setInterval(() => {
  if (!ownerAlive()) shutdown('owner process exited');
  else if (Date.now() - lastActivity > IDLE_TIMEOUT_MS) shutdown('idle timeout');
}, 60 * 1000);

The owner PID is the harness — resolved by start-server.sh as the grandparent of the script, since $PPID is just the ephemeral shell that launched it. touchActivity() resets the 30-minute idle clock on every HTTP request, every WebSocket message, and every screen change. On shutdown the server cleans up after itself:

server.cjs — shutdown
fs.writeFileSync(
  path.join(STATE_DIR, 'server-stopped'),
  JSON.stringify({ reason, timestamp: Date.now() }) + '\n'
);

If the owner PID is already dead at startup — common under WSL, Tailscale SSH, or cross-user setups where the reaper has moved on — monitoring is disabled and only the idle timeout applies. stop-server.sh escalates SIGTERM → SIGKILL and only rm -rf's /tmp sessions, preserving the persistent .superpowers/ mockups you might want to keep.

The non-blocking turn loop

The most important design lesson here isn't in the server at all — it's in what got deleted. The 2026-02-19 refactor diagnosed that the previous design ran a blocking wait-for-feedback.sh on TaskOutput(block=true, timeout=600s), which seized the TUI so the user literally couldn't type to Claude while it waited.

There is "no way for Claude to listen on two channels simultaneously within a single turn."2026-02-19 visual-brainstorming refactor design

Because Claude Code is turn-based, the fix was structural: delete wait-for-feedback.sh, make the browser a pure display, and let the terminal stay the always-open channel — bridged by the per-screen events file.

  1. Write a fresh screen

    A new, semantically named HTML file via the Write tool — never reuse names, never cat/heredoc.

  2. Summarize & end the turn

    Tell the user the URL plus a one-line summary, then yield. The terminal is now free.

  3. Read events next turn

    On the next turn, read state/events (the click stream) and merge it with whatever the user typed in the terminal.

  4. Iterate or advance

    Push waiting.html to clear stale content when returning to terminal-only questions, then go again.

Browser as display, terminal as channel, an events file as the bridge — that's the whole secret to a live companion that never blocks the conversation.
