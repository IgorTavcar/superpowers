The Methods

This is the full machinery. Fourteen plain-Markdown skills hand off to one another through explicit REQUIRED SUB-SKILL declarations and terminal states, forming a deterministic chain that carries an idea from rough conversation to merged code — never skipping a gate. Below: the lifecycle, the discipline rails that run through every step, and a reference catalog of all fourteen skills.

The end-to-end loop

Each skill knows what comes next. The handoffs aren't convention or hope — they're wired by name. brainstorming declares its only legal successor; writing-plans stamps every plan with the executor it requires; both executors call the same finishing skill. The result is a closed, auditable chain.

Skills reference each other with the superpowers:skill-name convention and bold handoff markers — never @-file links, which would force-load context before it's needed. A terminal state says where a skill is allowed to go next; a REQUIRED SUB-SKILL says where it must go. Threaded underneath every implementation step are the two discipline rails — test-driven development and systematic debugging — plus the honesty gate, verification-before-completion, in front of every claim of "done."

★

One chain, two layers. The catalog splits cleanly: lifecycle skills form the linear happy path, while discipline rails and meta skills are invoked by name from inside other workflows rather than sitting in the line.

Brainstorming → an approved spec

The loop starts by refusing to start. Before a single line of code, brainstorming teases a design out of conversation — one question at a time — and writes it to docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md, committed, only after you approve it.

This is enforced as a HARD-GATE. There is no "this is too simple to need a design" escape hatch — the skill carries an explicit anti-pattern rejecting exactly that rationalization:

"Do NOT invoke any implementation skill, write any code, scaffold any project, or take any implementation action until you have presented a design and the user has approved it."brainstorming/SKILL.md (HARD-GATE)

The nine-item checklist runs: explore context, offer a visual companion, ask clarifying questions one at a time, propose two or three approaches, present the design in sections (approval after each), write and commit the spec, run a spec self-review (a placeholder, consistency, scope, and ambiguity scan, fixed inline), let you review the written spec — and only then transition out. And it can transition exactly one way:

"The terminal state is invoking writing-plans. Do NOT invoke frontend-design, mcp-builder, or any other implementation skill. The ONLY skill you invoke after brainstorming is writing-plans."brainstorming/SKILL.md
✓

Why so strict? A locked terminal state means the agent can't quietly drift from "let's design this" into "I've already half-built it." The gate buys you a real, reviewed spec every time. The full mechanics live on the Brainstorming Engine page.

Writing plans → bite-sized TDD tasks

writing-plans turns the approved spec into an implementation plan written for an engineer with zero codebase context, saved to docs/superpowers/plans/YYYY-MM-DD-<feature>.md. The unit of work is deliberately tiny: every step is one action that takes two to five minutes.

Each task follows a fixed five-step TDD template — and the steps are the test-first cycle, baked into the document so an executing agent literally follows the rhythm:

writing-plans/SKILL.md · Task Structure
### Task N: [Component Name]

**Files:**
- Create: `exact/path/to/file.py`
- Modify: `exact/path/to/existing.py:123-145`
- Test: `tests/exact/path/to/test.py`

- [ ] **Step 1: Write the failing test**
- [ ] **Step 2: Run test to verify it fails**
- [ ] **Step 3: Write minimal implementation**
- [ ] **Step 4: Run test to verify it passes**
- [ ] **Step 5: Commit**

Every plan must open with a mandatory header that re-declares the executor for whatever agent picks it up later — the handoff is written into the document itself:

"REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task."writing-plans/SKILL.md (mandatory plan header)

A "No Placeholders" rule bans TBD, TODO, "add appropriate error handling," "Similar to Task N," and references to undefined types — the plan must be fully specified, not a sketch. Finally a three-point self-review (spec coverage, placeholder scan, type and signature consistency) reads the plan against the spec with fresh eyes, and an Execution Handoff offers the two paths: subagent-driven (recommended) or inline.

!

Never on main. Plans are never executed on main/master without explicit user consent — which is exactly why isolation comes next.

Isolate with git worktrees

Before execution, using-git-worktrees guarantees an isolated workspace — but it leads with detection, not creation. Step 0 compares GIT_DIR against GIT_COMMON (with a submodule guard via git rev-parse --show-superproject-working-tree) to notice when the work is already isolated, and skips creation if so.

The governing rule is blunt: never fight the harness. If the platform offers a native worktree tool (EnterWorktree, /worktree, a --worktree flag), the skill prefers it over a manual git worktree add, because:

"Using git worktree add when you have a native tool creates phantom state your harness can't see or manage."using-git-worktrees/SKILL.md (Step 1a)

Only as a fallback does it reach for raw git — and even then with guardrails. It picks a directory by priority (user preference > existing .worktrees/ > worktrees/ > the global legacy location > default .worktrees/), then runs a mandatory git check-ignore safety verification so the new worktree directory can't pollute the tree. If sandbox permissions block creation, it falls back to working in place.

  1. Detect

    Compare GIT_DIR ≠ GIT_COMMON, with a submodule guard. Already isolated? Skip ahead.

  2. Create (native first)

    Prefer the harness's own worktree tool; fall back to a gitignore-verified git worktree add.

  3. Set up

    Auto-detect and run project setup — npm, cargo, pip, poetry, go.

  4. Baseline

    Confirm a clean test baseline before implementing anything, so later failures are unambiguously yours.

Subagent-driven development & the two-stage review

The recommended executor is subagent-driven-development: the controller reads the plan once, extracts every task's full text and context into TodoWrite, then dispatches a fresh implementer subagent per task. Crucially, the controller pastes the full task text into the prompt — it never makes the subagent read the plan file.

Fresh subagent per task + two-stage review (spec then quality) = high quality, fast iteration.

The defining mechanic is the order of review. After an implementer reports back, a spec-compliance reviewer runs FIRST — did it build exactly what was asked, nothing more, nothing less? Only once spec compliance is clean does a code-quality reviewer run SECOND — is it well-built? Each reviewer triggers a fix-and-re-review loop on the same implementer subagent until it's green. Running quality before spec is an explicit Red Flag.

The spec reviewer is instructed to be paranoid. Its prompt opens by telling it not to trust the implementer's own account:

"The implementer finished suspiciously quickly. Their report may be incomplete, inaccurate, or optimistic. You MUST verify everything independently."subagent-driven-development/spec-reviewer-prompt.md

It does that by reading the actual code line-by-line for missing requirements, extra unrequested work, and misunderstandings, returning ✅ or ❌ with file:line. Three sibling prompt files encode the whole dance: implementer-prompt.md, spec-reviewer-prompt.md, and code-quality-reviewer-prompt.md (which itself reuses the shared code-reviewer.md template). Implementers report one of four statuses:

DONE

Task complete, tests pass, committed and self-reviewed.

DONE_WITH_CONCERNS

Finished, but flags something worth a second look.

NEEDS_CONTEXT

Missing information it can't safely guess at — asks rather than invents.

BLOCKED

Cannot proceed. Bad work is worse than no work.

The skill also offers model-selection guidance — a cheap model for one-or-two-file mechanical tasks, a capable one for architecture and review — and forbids dispatching multiple implementers in parallel for the same plan. For platforms without strong subagent support there's an inline alternative, executing-plans: load the plan, review it critically and raise concerns before starting, TodoWrite, execute each bite-sized step exactly, run all verifications, then hand off to finishing. It announces itself at the start and openly recommends switching to subagent-driven-development when subagents are available.

Discipline rails

Two skills run through every implementation step as always-on guardrails. Both are framed as Iron Laws with rationalization tables, so an agent can't reason its way out under pressure.

Rail one · Test-driven development
!

The Iron Law. NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST.

The cycle is RED → Verify-Red → GREEN → Verify-Green → REFACTOR, and the two verify steps are mandatory. Watching the test fail isn't optional ceremony — it's the only proof the test tests the right thing:

"If you didn't watch the test fail, you don't know if it tests the right thing."test-driven-development/SKILL.md

Wrote code before its test? The rule is uncompromising — delete it. "Delete means delete," with no keeping it around "as reference." Verify-Red requires the test to fail for the right reason (a real assertion failure, not an error); Verify-Green requires it to pass with all other tests green and pristine output. This is why writing-plans bakes the five-step cycle into every task and why subagents are explicitly told to use it.

Rail two · Systematic debugging
!

The Iron Law. NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST.

When anything breaks, four phases funnel toward the actual cause instead of stacking fixes on symptoms:

PhaseWhat happens
1 · Root causeRead the errors, reproduce, check recent changes, instrument each component boundary, trace data flow.
2 · Pattern analysisFind a working example, read the reference completely, list every difference.
3 · HypothesisForm a single specific hypothesis; test it with the smallest change, one variable at a time.
4 · ImplementationWrite a failing test FIRST (via TDD), apply ONE fix, verify.

Phase 4 carries an escalation rule. If a fix fails and you've tried fewer than three times, return to Phase 1 with the new information. But:

"If ≥ 3: STOP and question the architecture. This is NOT a failed hypothesis — this is a wrong architecture."systematic-debugging/SKILL.md (Phase 4)

A companion technique, root-cause-tracing.md, teaches tracing backward from a deep symptom up the call stack to the original trigger — "NEVER fix just where the error appears" — then adding defense-in-depth at each layer so the bug becomes impossible. When manual tracing dead-ends, it instruments with new Error().stack before the dangerous operation and bisects with a shell tool to find which test pollutes shared state:

./find-polluter.sh '.git' 'src/**/*.test.ts'

In one worked example, a stray .git directory was traced through five levels to a test fixture returning an empty tempDir — and the source fix plus four layers of defense-in-depth produced 1847 passing tests with zero pollution.

Verify, review, finish

Three skills guard the exit. They share a theme: assertions must be backed by evidence, feedback must be evaluated on its merits, and a branch isn't done until you've chosen what to do with it.

The honesty gate

verification-before-completion sits in front of every "complete," "fixed," or "passing" — including trusting a subagent's success report.

!

The Iron Law. NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE — if you haven't run the verification command in this message, you cannot claim it passes.

Its five-step Gate Function — IDENTIFY the proving command, RUN it fresh and in full, READ the output and exit code and failure count, VERIFY the output actually confirms the claim, THEN claim — treats skipping any step as dishonesty. Agent delegation is never trusted on the agent's word; the controller checks the VCS diff instead. And a regression test isn't "added" until it survives a full red-green cycle:

Write → Run (pass) → Revert fix → Run (MUST FAIL) → Restore → Run (pass)
Receiving review

The review loop has two mirrored skills. requesting-code-review dispatches a Senior Code Reviewer subagent over an explicit SHA range with the code-reviewer.md template, and acts on findings by severity — fix Critical immediately, Important before proceeding, note Minor. The reviewer is told to calibrate, not catastrophize:

"Categorize issues by actual severity. Not everything is Critical. Acknowledge what was done well before listing issues — accurate praise helps the implementer trust the rest of the feedback."requesting-code-review/code-reviewer.md

Its mirror, receiving-code-review, governs how feedback is taken: a six-step pattern (READ → UNDERSTAND → VERIFY → EVALUATE → RESPOND → IMPLEMENT, one item at a time), a YAGNI grep before implementing any "professional" feature an external reviewer suggests, and push-back with technical reasoning when the reviewer is wrong. It bans performative agreement outright:

★

No reflexive flattery. "You're absolutely right!", "Great point!", and any gratitude are forbidden. "If you catch yourself about to write 'Thanks': DELETE IT. State the fix instead."

Finishing the branch

finishing-a-development-branch closes the loop. It verifies tests pass (stopping if they don't), detects the environment via GIT_DIR vs GIT_COMMON, determines the base branch with git merge-base, and presents exactly four options (three for a detached HEAD, where merge is dropped):

finishing-a-development-branch/SKILL.md · the menu
Implementation complete. What would you like to do?

1. Merge back to <base-branch> locally
2. Push and create a Pull Request
3. Keep the branch as-is (I'll handle it later)
4. Discard this work

Each path is precise: merging cds to the main root, checks out the base, pulls, merges, re-runs tests, then cleans up; the PR path uses gh pr create with a heredoc Summary / Test Plan body and deliberately does not remove the worktree; discard requires you to type the word discard. Cleanup runs only for merge and discard, and only on provenance-owned worktrees — those under .worktrees/, worktrees/, or ~/.config/superpowers/worktrees/ — via git worktree remove and prune from the main root. It never touches a harness-owned workspace, and never deletes a branch before removing its worktree.

The two meta skills bracket everything else. using-superpowers is the bootstrap that forces a skill check "before any response or action, even a 1% chance it applies," and sets the priority order — user instructions > skills > system prompt. writing-skills is the reflexive authoring skill that produced every SKILL.md by applying TDD to documentation itself ("NO SKILL WITHOUT A FAILING TEST FIRST").
